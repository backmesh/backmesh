Upgrade with `backmesh upgrade`; there's no need to uninstall. From v0.6.0, runners keep starting throughout: anycloud 0.1.83's API still takes v0.6.0's listener, so no org pauses. From v0.5.7, runners pause from the control plane's update until each org's listener restarts, as v0.6.0's notes describe. As with v0.6.0, `upgrade` re-applies the AWS and GCP role setup on every run, so sign `aws` and `gcloud` in first.

### Changes

- **The control plane moves to anycloud 0.1.83, and runner VMs start sooner.** On AWS, a zone with no spot capacity is now skipped within a second instead of after 25–55 s of retries ([anycloud#35](https://github.com/anycloud-sh/anycloud/pull/35)). From a runner VM's network start to its container's start, anycloud measured AWS's median falling from 13.3 to 12.1 s and Azure's range from 26.5–32.9 s to 21.6–24.4 s ([anycloud#26](https://github.com/anycloud-sh/anycloud/pull/26)), and GCP's median from 40.4 to 29.1 s ([anycloud#31](https://github.com/anycloud-sh/anycloud/pull/31)). Those are measurements of the VM's start, not of whole jobs.
- **AWS labels try `m8a` first.** Every AWS label but KVM and GPU, spot and on demand, now tries AMD's `m8a`, then `m8i`, `m7a`, `m7i` and `m6a` as before: `m8a` builds about 1.3 times as fast, and whole jobs run about 1.2 times as fast. A zone without spot `m8a` costs a job seconds, as anycloud moves on as soon as one refuses. It counts against the same quotas, and a job costs less or about the same. `backmesh upgrade` lists the labels under "New VM types or regions" and asks before it applies them. ([#119](https://github.com/backmesh/backmesh/pull/119); speed: [anycloud#30](https://github.com/anycloud-sh/anycloud/pull/30), spot landing: [anycloud#35](https://github.com/anycloud-sh/anycloud/pull/35))
- **The cloud CLIs install without apt.** On first use, `az`, `gcloud` and `aws` now install from pinned vendor releases: Azure CLI 2.93.0, Google Cloud CLI 593.0.0 and AWS CLI 2.40.4, the versions GitHub's Ubuntu 24.04 image has. Each release is checked against its SHA-256 or AWS's signature, and failed downloads are retried. apt package indexes are no longer fetched, so a mirror mid-sync or returning a 5xx no longer fails the step. `gsutil` now installs on first use too. ([#115](https://github.com/backmesh/backmesh/pull/115))
- **First use installs the right package.** On first use, `psql` and the other PostgreSQL client commands now install the client; until now they installed only its wrapper, which failed. `dotnet` now installs the .NET 10 SDK, not a host without an SDK. Commands that would install the wrong tool now fail as not found, as they do on any runner without them: `swift` installed OpenStack's client, and `firefox` and `chromium-browser` installed Ubuntu's snap stubs, which can't run in the runner's container. `chromedriver` and `bazel` now come from pinned releases (below), not a snap stub and Bazel 4.2.3. ([#122](https://github.com/backmesh/backmesh/pull/122))
- **`gh` and Docker match GitHub's image.** The runner image now has GitHub CLI 2.105.0, from GitHub's release, instead of Ubuntu's 2.45.0, so `gh attestation` and `gh api --slurp` work. It also has Docker CLI 28.0.4, Buildx 0.39.1 and Compose 2.38.2, up from 27.5.1, 0.20.1 and 2.33.0. docker/setup-buildx-action uses the runner's Buildx unless a workflow sets a `version`. ([#123](https://github.com/backmesh/backmesh/pull/123))
- **GCP's on-demand labels try AMD's newest VMs first.** `backmesh-od-4`, `backmesh-od-8` and `backmesh-od-16` on GCP now try `c4d` (Zen 5), then `c3d` (Zen 4), before `n2` and `n2d`; `backmesh-od-2` doesn't change. At 4 vCPUs, `c4d` built in half of `n2`'s time, at 0.78 of its cost per job with its Hyperdisk Balanced disk, and `c3d` in 0.71 of it at 0.76. A `c4d` VM has 3.875 GiB of memory a vCPU, so `backmesh-od-4` may get 15 GiB, not 16. `us-south1` offers neither, and `us-west2` and `us-west3` no `c3d`, so jobs there start on `n2` or `n2d`. Spot and KVM labels don't change. On-demand runners now also count against GCP's `C4D_CPUS` and `C3D_CPUS` quotas, which install names with the others to raise, and a `c4d` runner's disk against the region's Hyperdisk Balanced quotas. ([#126](https://github.com/backmesh/backmesh/pull/126); measured: [anycloud#38](https://github.com/anycloud-sh/anycloud/pull/38))
- **Rust, PowerShell, Go, Java and Chrome install on first use.** As the cloud CLIs do, each now installs from a pinned, checksummed vendor release the first time a job calls it, from any caller, including `sh` scripts such as `./gradlew` and JavaScript actions: Rust 1.100.0 with rustup 1.29.3, clippy and rustfmt (`cargo`, `rustc`, `rustup` and the rest), PowerShell 7.6.10 (`pwsh`, and so `shell: pwsh`), Go 1.26.11 (`go`, `gofmt`), Temurin 17.0.21.1 (`java`, `javac`, `jar`, `keytool`), and Chrome and ChromeDriver 158.0.8127.36 (`google-chrome`, `chromedriver`), the versions GitHub's Ubuntu 24.04 image has. Until now `cargo` and `rustc` installed Ubuntu's Rust 1.75, too old for edition 2024 crates, `go` Go 1.22 and `java` OpenJDK 17, and only from a bash step; `pwsh` and `google-chrome` weren't found. Rust's toolchain is installed as `stable`, so dtolnay/rust-toolchain@stable finds it, and `~/.cargo/bin` is on PATH, as on GitHub's image. `JAVA_HOME`, `JAVA_HOME_17_X64` and `CHROMEWEBDRIVER` are set as on GitHub's image, and Chrome is also at `/usr/bin/google-chrome` and `/opt/google/chrome/chrome`, where `channel: 'chrome'` looks. Until the first `java` call installs the JDK there, `$JAVA_HOME` holds only the shims: `jni.h`, `libjvm.so` and `jlink` appear then. Chrome always runs with `--no-sandbox`, as the runner's container can't make the namespaces its sandbox needs: a page a job opens isn't sandboxed from the job's container. ([#124](https://github.com/backmesh/backmesh/pull/124))
- **CMake, Ninja, Maven, Kind, Kustomize and Bazelisk are preinstalled**, at the versions GitHub's Ubuntu 24.04 image has: CMake 3.31.6, Ninja 1.13.2, Maven 3.10.2, Kind 0.33.0, Kustomize 5.8.3 and Bazelisk 1.28.1, as both `bazelisk` and `bazel`. Bazelisk replaces Bazel 4.2.3, which ignored `.bazelversion`: Bazel itself isn't in the image, and a job's first `bazel` call downloads the version `.bazelversion` names. Until now `cmake`, `ninja` and `mvn` installed Ubuntu's older 3.28.3, 1.11.1 and 3.8.7 on first use, and only from a bash step, so a build script's `cmake` failed; `kind` and `kustomize` weren't found. Kind's clusters run on the VM's Docker and are reachable from the job, whose network is the VM's. The image's compressed layers grow by 46 MB, 6%, which added about 1 s to a runner's pull on AWS (measured). On GCP, whose pull took 19.7 s for 753 MB, and on Azure, 16.5 s for the same image, it should add about 1.2 s and 1 s (estimated, not measured). ([#125](https://github.com/backmesh/backmesh/pull/125))
